# Архитектура Парсера и Механизм Идентификаторов (IDs)

Данный документ описывает внутреннюю архитектуру сканера файлов Figma, устройство локальных и глобальных идентификаторов компонентов, а также особенности сопоставления элементов в аналитике дизайн-системы (`DS Analysis`).

---

## 1. Архитектура Сканера и Парсера (Rust)

Сканирование файлов Figma осуществляется высокопроизводительным сканером на Rust ([parser.rs](file:///D:/Figma%20plugins/Components%20dashboard/v1/apps/api-rust/src/scanner/parser.rs)).

### Основной цикл обхода (`parse_figma_tree`)
- **Алгоритм**: Обход дерева узлов Figma в глубину (**DFS — Depth-First Search**) с использованием стека `StackItem`.
- **Входные данные**: JSON-документ файла/страницы Figma, ID сессии (`session_id`), ключ файла (`file_key`), а также словарь компонентов `components`.
- **Пакетная запись в БД**: Ноды записываются в SQLite батчами по 2,000 элементов в рамках одной транзакции (`INSERT OR REPLACE INTO nodes ...`), что обеспечивает обработку сотен тысяч узлов в секунду.

## 2. Типы Идентификаторов Нод в Figma

В системе используются три основных типа идентификаторов:

| Поле в БД | Описание | Пример | Область уникальности |
| :--- | :--- | :--- | :--- |
| **`id`** (`node_id`) | Идентификатор узла внутри файла Figma | `1089:131395` | Уникален **только в рамках одного файла** |
| **`component_id`** | ID родительского/мастер-компонента, на который ссылается `INSTANCE` | `7216:38247` | Уникален **в рамках файла-источника** |
| **`published_key`** | Глобальный уникальный 40-символьный хэш опубликованного компонента | `4c55dae4d642344be7b6e7d784...` | **Глобально уникален** во всей Figma |

### В чем ключевая разница:
1. **Локальный ID (`id` / `component_id`)**: Назначается Figma при создании элемента в конкретном документе. Если файл скопировать или залинковать в другой проект, ID внутренних элементов могут совпадать или переназначаться локально.
2. **Глобальный ключ (`published_key`)**: Генерируется Figma при публикации компонента в библиотеку (UI Kit). Именно по `published_key` Figma отслеживает связи между мастер-компонентом из UI Kit и миллионами его инстансов во всех продуктовых макетах.

## 3. Причина пропусков `published_key` у сторонних инстансов

### Как Figma REST API отдаёт компоненты:
1. При запросе конкретных страниц файла (`GET /v1/files/{key}/nodes?ids={page_id}`) Figma возвращает объект `components` в корне ответа.
2. **Ограничение Figma API**: Этот объект `components` содержит пары `component_id -> key` **только для тех компонентов, которые были созданы и опубликованы непосредственно в самом сканируемом файле**.
3. Узлы типа `INSTANCE`, импортированные из внешних библиотек (например, из общего `Reference UI Kit`), в теле JSON содержат только свой `componentId` (например, `"223:6278"`), но не содержат поля `key`.

### Результат при сканировании:
- В **файле библиотеки (Reference UI Kit)** все компоненты получают `published_key`, так как они там созданы.
- В **файлах-потребителях (Consumer Files)** локальный словарь `components` от Figma равен `{}` (пуст). Поэтому при первичном сканировании все внешние инстансы сохраняются с `published_key = NULL`.

## 4. Механизм работы `backfill.rs` и почему он пропускал инстансы

Скрипт фоновой простановки ключей [backfill.rs](file:///D:/Figma%20plugins/Components%20dashboard/v1/apps/api-rust/src/bin/backfill.rs):

```rust
// backfill.rs делает запрос по страницам файла:
let url = format!("https://api.figma.com/v1/files/{}/nodes?ids={}&geometry=none", file_key, page_id);
```

1. Скрипт запрашивал `/v1/files/{file_key}/nodes?ids={page_id}` для каждого файла.
2. Ответ API Figma возвращал `200 OK`, но словарь `components` в ответе был пуст для файлов макетов (так как макеты используют внешние библиотеки, а не создают свои компоненты).
3. Скрипт завершал работу без ошибок (`Status: 200`), но обновлял `0` записей для продуктовых файлов.

### Корректный подход к дозаполнению `published_key`:
Чтобы заполнить `published_key` у 100% инстансов без обращения к Figma API:
- **Сопоставление по локальной БД**: В базе данных уже сохранены все мастер-компоненты эталонного UI Kit с их `id` и `published_key`.
- **Запрос связи**:
  ```sql
  UPDATE nodes
  SET published_key = (
      SELECT master.published_key 
      FROM nodes master 
      WHERE master.id = nodes.component_id 
        AND master.published_key IS NOT NULL 
      LIMIT 1
  )
  WHERE type = 'INSTANCE' AND (published_key IS NULL OR published_key = '');
  ```

## 5. Как работает аналитика в `DS Analysis` (`ds_usage`)

Контроллер `ds_usage` ([search.rs](file:///D:/Figma%20plugins/Components%20dashboard/v1/apps/api-rust/src/controllers/search.rs#L204-L276)):

1. **`ref_session`**: Находит последнюю сессию сканирования для файла, отмеченного флагом `is_reference = 1` (Reference UI Kit).
2. **`target_session`**: Находит последнюю сессию выбранной пользователем команды (например, `Retention`).
3. **`ref_components`**: Извлекает мастер-компоненты и варианты из эталонного кита.
4. **`usages`**: Считает количество инстансов в целевой сессии, сгруппированных по `published_key`:
   ```sql
   WHERE i.session_id = (SELECT id FROM target_session)
     AND i.type = 'INSTANCE'
     AND i.published_key IS NOT NULL AND i.published_key != ''
   ```
5. **Соединение (JOIN)**: Соединяет `ref_components` и `usages` по условию `r.published_key = u.published_key`.

> **Важно**: Если у инстанса в файле команды `published_key` не проставлен (`NULL`), он автоматически отфильтровывается на шаге `usages` и не попадает в итоговый отчёт `DS Analysis`.

## 6. Нюанс интерфейса: Почему "DS Kit" может выдавать везде нули?

Очень важно понимать, что вкладка **DS Kit Stats** в React-приложении берет статистику *строго по той команде, которая сейчас выделена в левом сайдбаре (свойство `selectedTeam` в `TeamsContext`)*. 

**Сценарий пустых результатов:**
Если пользователь ожидал увидеть статистику команды `Retention`, но в сайдбаре у него была выделена `Engagement` (и сессия Engagement при этом поставлена на паузу `paused` или не завершена `completed`), `target_session` в запросе SQL вернет пустой результат.
Из-за этого `LEFT JOIN` оставит для всех мастер-компонентов из эталонного кита значение `usage_count = 0`.

**Решение:** Для просмотра отчета конкретной продуктовой команды, необходимо **сначала явно выбрать её в сайдбаре сайдбаре команд**, и только после этого открывать вкладку с дашбордом DS Kit.
