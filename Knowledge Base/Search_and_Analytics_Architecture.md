# Архитектура Поиска и Аналитики (Search & Analytics)

В данном документе описана архитектура модуля глобального поиска и аналитики (статистики по свойствам), который позволяет взаимодействовать с огромным набором (>12 млн) компонентов Figma.

## 1. Обзор модуля (Overview)
Модуль обеспечивает:
- Сквозной **Full-Text Search (FTS5)** по всем файлам рабочего пространства.
- Динамическую **агрегацию статистики** (состояния, размеры, иконки — Properties) прямо из сырого JSON.
- Абсолютно модульную структуру на фронтенде (разделение Data Layer и Presentation Layer).
- Изолированные контроллеры в Rust-бэкенде.

---

## 2. Структура файлов и Модули (Structure)

### Frontend (React / TypeScript)
Локация: `apps/web/src/modules/Search/`

Фронтенд избавлен от монолитной архитектуры и построен на изолированных паттернах:
- **`hooks/useSearch.ts`** — «Мозг» модуля. Централизованно управляет состоянием поиска (`query`, `teamFilter`, `propertyFilters`), дебаунсит инпуты (чтобы не спамить API каждую миллисекунду) и синхронизирует результаты `stats` и `nodes`.
- **`SearchView.tsx`** — Контейнерный (Layout) компонент. Не содержит бизнес-логики, только сетку (верстку) и вызов хука `useSearch`.
- **`components/SearchFilters.tsx`** — Боковая панель для настройки типов нодов (Variant/Component) и выбора режима отображения (Flat/Grouped).
- **`components/GroupedResultsTree.tsx`** — Крайне важный компонент, который использует **`react-virtuoso`** для виртуального скролла. Позволяет браузеру не падать при рендере 50,000 сложных DOM-результатов поиска.
- **`components/SearchStats.tsx`** — Панель аналитики, визуализирующая глобальные свойства компонентов по всему воркспейсу.

### Backend (Rust / SQLite)
Локация: `apps/api-rust/src/controllers/search/`

Огромный монолитный файл `search.rs` расщеплён на логические домены:
1. **`global.rs` / `search_global`**
   - Выполняет матчинг компонентов. Работает с FTS5 `nodes_search MATCH ?` для молниеносного ответа. Умеет отдавать как плоский список, так и предсгруппированный (Grouped BY).
2. **`stats.rs` / `search_global_stats`**
   - Движок аналитики. Содержит тяжелую в SQL операцию по парсингу JSON (`json_each`) для извлечения свойств "на лету" из `node_metadata.properties_json`.
3. **`usage.rs` / `ds_usage`**
   - Механизм Dependency Analysis — связывает `INSTANCE` с `published_key` для построения статистики внедрения дизайн-системы (DSKit Adoption).

## 3. Ключевая бизнес-логика (Key Logic)
- **Агрегация JSON-свойств:** База данных хранит свойства (Properties: Size, State, Has Icon) как строку JSON. Rust-бэкенд не пытается десериализовать их в памяти. Вместо этого SQLite при помощи `json_each` и `json_extract(nm.properties_json, '$."Size".value')` достаёт и подсчитывает свойства в C-прослойке.
- **Актуальные сессии (CTE `latest_sessions`):** Чтобы поиск не выдавал "призрачные" ноды из прошлых сканирований, все запросы оборачиваются в `WITH latest_sessions AS (...)`, гарантируя выборку только финальных или текущих сессий.

---

## 4. Узкие горлышки (Bottlenecks)
1. **CPU Intensive `json_each`:** При росте базы (например, до 50+ миллионов компонентов), парсинг JSON строка за строкой через `json_each` в SQLite без индексов упрется в процессор. Запрос статистики может начать занимать >5-7 секунд.
2. **Память Фронтенда (Memory Heap):** Несмотря на виртуальный рендеринг (`react-virtuoso`), бэкенд возвращает JSON массива в RAM браузера. Браузер Chrome может упасть с `Out of Memory`, если бэкенд вернет список на 200,000 нод. Сейчас стоит искусственный блок `LIMIT 50000`.
3. **Сжатые сроки Timeout-ов (Busy DB):** Если запрос на поиск совпадает со вставкой батча парсера в SQLite (`os error 5 / busy`), долгий `SELECT` может заблокировать WAL-журнал базы.

## 5. Улучшения на будущее (Future Improvements)
* **SQLite Generated Columns:**
  - Самые популярные пропертисы (e.g. `Size`, `State`, `Type`) стоит вынести на бэкенде в индексированные Generated Columns:
    `ALTER TABLE node_metadata ADD COLUMN prop_size TEXT AS (json_extract(properties_json, '$."Size".value'));`
    Это ускорит фильтрацию в аналитике с `O(N)` до `O(log N)` за счет B-Tree индекса.
* **Кэширование на Backend (Cache):**
  - Подключить `moka` (хит-кэш уровня Rust) для рута `/global/stats`. Глобальная статистика без фильтров меняется редко (до обновы ДС). Раздача кэша за 1ms спасет базу от стресса.
* **Cursor Pagination (Пагинация):**
  - Полностью отказаться от `LIMIT 50000` в SQLite. Запрашивать результаты у бэкенда курсорами (по 500 штук), когда `Virtuoso` почти доскроллил до конца списка. Это радикально облегчит сетевой Payload (Response Data) и потребление памяти в браузере.
