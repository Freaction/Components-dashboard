# Инструкции и правила проекта для AI-агента

## 1. Архитектура и размер файлов

* Лимит строк: Дели каждый новый модуль на файлы объемом **не более 200 строк**.

* Модульность: Пиши емкий, декомпозированный и максимально производительный код. Избегай монолитных файлов.

## 2. Чистота кода и комментарии (Strict Rules)

## 3. Компоненты, токены и темы

* **Дизайн-система:** Всегда строй интерфейсы строго на design-токенах и компонентах.

* **Переиспользование:** Выноси любые повторяющиеся UI-элементы в отдельные компоненты и переиспользуй их.

* **Темы:** Обязательная встроенная поддержка **светлой и темной тем** (Light/Dark mode) для всех UI-элементов и компонентов.

## 4. Сборка и запуск Rust API

* **Только release:** API запускается и собирается **исключительно** через `--release` (`dev.bat`, `npm run dev:start`). Debug-сборка компилирует bundled SQLite с `-O0` и работает в разы медленнее — никогда не запускай `cargo run` без `--release`.

* **Изоляция артефактов:** debug- и release-бинарники лежат в разных каталогах (`target/debug/`, `target/release/`) и не смешиваются. Работающий бинарь — `target/release/api-rust.exe`.

* **Порт:** всегда 3002 — этот адрес зашит во фронтенде. Переопределяется только переменной `API_RUST_PORT` (для тестового запуска рядом с рабочим сервером). Переменную `PORT` использовать нельзя: `db.rs` через `dotenvy` подгружает корневой `.env`, где `PORT=3001` принадлежит tokens-parser.

## 5. Работа с базой (data/main.sqlite, ~78 ГБ)

* **Данные бесценны:** никогда не выполняй записывающие запросы к боевой базе без явного согласия. Для анализа открывай её только как `file:data/main.sqlite?immutable=1` в режиме `-readonly`.

* **Планы запросов проверяй с параметрами, а не с литералами:** SQLite строит РАЗНЫЕ планы для `MATCH 'button*'` и `MATCH ?`. Проверенный на литералах запрос может уйти в полный скан на связанных параметрах. Всегда снимай `EXPLAIN QUERY PLAN` с `?`.

* **Фиксируй порядок соединений через `CROSS JOIN`:** статистики (`sqlite_stat1`) в базе нет, поэтому планировщик легко выбирает `nodes`/`node_metadata` ведущей таблицей и сканирует десятки миллионов строк. `CROSS JOIN` запрещает переупорядочивание.

* **Поисковые стратегии** (`controllers/search/strategy.rs`) выбираются дешёвыми пробами по размеру среза и числу совпадений FTS. Меняя SQL поиска, обязательно перезамеряй худшие случаи: редкий запрос + частый тип + маленькая команда.

## 6. Свойства компонентов (node_props)

* **Источник правды для свойств** — таблица `node_props(session_no, node_id, key, value)`, а не `properties_json`. Статистика в Analytics и фильтры по свойствам читают только её; `json_each` по `node_metadata` больше не используется.

* **Значение вычисляется при записи** по правилу `value` → `defaultValue` → `type` → `Unknown`, булевы приводятся к `1`/`0` — так же, как это делал SQLite `json_extract` + `CAST`.

* **Парсер заполняет `node_props` сам** при сканировании, поэтому повторная миграция для новых сессий не нужна. Разовый бэкфилл существующих данных — `cargo run --release --bin migrate_props`; он возобновляемый (курсор в `migration_state`) и печатает прогресс с ETA.

* **Пустые метаданные не пишутся:** если у узла все пять JSON-полей пусты, строка в `node_metadata` не создаётся; пустые `{}`/`[]` сохраняются как NULL. UI это учитывает.

* **`PRAGMA recursive_triggers=ON` обязателен.** Без него `INSERT OR REPLACE` в `nodes` не вызывает триггер `nodes_ad`, и каждое повторное сканирование оставляет в FTS документ-призрак с устаревшим именем.

* **Проверка парсера** — `cargo run --release --bin check_parser -- <путь к временной БД>`: прогоняет дерево через `parse_figma_tree` и печатает содержимое `nodes`, `node_metadata`, `node_props` и счётчик документов FTS. Запускай после любых правок парсера.
